## Findings

### Blocking: resolution transaction writes immutable attempt evidence

- **Source:** `src/features/practice/infrastructure/repositories.ts:301-306` appends a resolution and then calls `tx.update(practiceAttemptEvidence).set({ label })`. `db/migrations/0017_learner_practice_selection.sql:47-53` installs `practice_attempt_evidence_immutable`, which rejects every update or delete of that table. `src/app/api/evidence/route.ts:39-42` converts an unexpected mutation failure to `EVIDENCE_UNAVAILABLE` (HTTP 503).
- **Trigger:** An authorised academic lead or admin submits any valid resolution for a submitted item with automatic outcome `needs_teacher_review`.
- **Consequence:** PostgreSQL aborts the transaction, rolling back the appended resolution and its success audit. The staff member gets a 503 rather than a saved effective outcome. This fails Story 4.3 acceptance criteria 1 and 3 (`spec-4-3-resolve-uncertain-item-outcomes.md:65-70`) and violates the Epic constraint that resolution must preserve immutable submitted evidence (`epic-4-context.md:30-31`).
- **Disposition:** Fix now. Do not update `practice_attempt_evidence`; calculate any current recommendation projection without mutating immutable submission evidence, then cover the committed repository transaction against PostgreSQL.
- **Prevention lesson:** Any derived-projection rebuild must explicitly inventory database immutability triggers before implementation and receive a database-backed test through the real repository transaction.

### Verification gap: resolution flow has no browser end-to-end coverage

- **Source:** `tests/e2e/teacher-evidence.spec.ts:10-20,37-48,55-78` seeds and authenticates only a `teacher` with an `incorrect` item. It exercises dashboard filters and read-only drill-down only. Story 4.3 itself records the residual risk that the resolution form's complete browser journey is not executed (`spec-4-3-resolve-uncertain-item-outcomes.md:103-107`).
- **Trigger:** The academic-lead/admin resolution form, success refresh, or stale-conflict recovery regresses in the browser.
- **Consequence:** Role-gated mutation, request payload and retry behaviour can ship broken even while the existing E2E test passes. The missing E2E would also have exposed the blocking repository failure above.
- **Disposition:** Fix now. Add an authenticated academic-lead/admin journey that resolves an uncertain item, asserts the refreshed effective outcome, and verifies stale-revision refresh/retry behaviour at narrow and desktop widths.
- **Prevention lesson:** New role-gated mutation UI must have at least one authenticated success and expected-conflict E2E path before a story is marked done.
