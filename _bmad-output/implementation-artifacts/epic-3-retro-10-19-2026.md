## Findings

### Blocking: answers given offline or restored from a draft are silently lost at submission

- **Source:**
  - `src/features/practice/ui/practice-player.tsx:49-50`: the `online` handler only changes the status label.
  - `practice-player.tsx:55-61`: draft hydration only updates local state.
  - `practice-player.tsx:79`: `request` returns early when offline.
  - `practice-player.tsx:149`: the confirmation counts local responses.
  - `src/features/practice/infrastructure/repositories.ts:235-240`: submission scores only server-stored responses.
- **Trigger:** a learner answers while offline (or reloads and the draft restores answers), reconnects, and submits without re-selecting each answer.
- **Consequence:** the confirmation says the item is answered, but the immutable submitted result records it as `unanswered`. Reproduced in Chromium at a 375px viewport: question 3 was answered `dog` offline, then the connection was restored. The confirmation showed "2 answered and 1 unanswered" (correct for the screen), and the review showed question 3 as "No answer / unanswered".
- **Why it matters:** this breaks Story 3.4 ("retry is explicit or revision-aware after reconnect", `spec-3-4:35`) and FR-9. It is exactly the "answer-loss" critical completion issue the PRD pilot criteria forbid.
- **Disposition:** fix now.
- **Prevention:** a browser journey that goes offline, answers, reconnects and submits would have caught it.

### High: an answer typed just before `Submit anyway` can be dropped (plausible, not reproduced)

- **Source:** `practice-player.tsx:100-105` (`save` awaits the local draft write before joining `mutationQueue`), `:124-129` (submit awaits only the existing queue), `:146` (note-taking saves on blur), and the confirmation panel at `:149`.
- **Trigger:** with the confirmation panel open, the learner edits a note-taking field and presses `Submit anyway` directly.
- **Consequence:** submit can finalise with the older revision. The late save then fails with `ATTEMPT_FINALISED` and the answer is lost. A related silent skip exists: `request` returns `undefined` with no notice when `saving` is already true (`:79`).
- **Disposition:** fix now, together with the blocking finding. Submission must wait for every pending local edit to be server-confirmed.

### High: learner recommendation diverges from the PRD evidence rule and exposes internal IDs

- **Source:**
  - `repositories.ts:253` computes one `evidenceFor(...)` label for the whole attempt.
  - `repositories.ts:279-283` writes that label for every primary target, supporting target and `guidanceId` as a "practice area".
  - `src/features/practice/application/practice.ts:36` requires three assessable *area rows*, and `:44-46` publishes `practiceArea` as the raw area ID.
  - `src/features/practice/ui/learner-home.tsx:8` renders "These activities support your practice area: {id}" and lists recommended titles as plain text.
- **Trigger and consequence:**
  - The PRD rule is "at least three assessable outcomes … per paper/part and language target". In the browser walkthrough, a learner with three assessable outcomes in one set still received no recommendation, because one attempt yields only two area rows (target plus guidance).
  - When a recommendation does appear, its practice area may be a UUID, or a guidance ID that is not a language target.
  - Recommended sets cannot be started from the recommendation.
  - The learner-facing label can disagree with the teacher dashboard, which uses the correct per-target rule over `submitted_evidence_facts`.
- **Disposition:** fix now.

### High: post-submission review is not the calm, comprehensible summary the experience contract requires

- **Source:**
  - `src/features/practice/ui/submitted-practice-review.tsx:5` shows only "Question {n}", with no prompt or media reference (contrast `EXPERIENCE.md:68`).
  - The same file renders the raw outcome (`incorrect`, `unanswered`, `needs teacher review`).
  - It repeats one set-level evidence label under every question (from `repositories.ts:253,267`).
  - It has no "practice feedback, not an official result" statement.
  - `practice-player.tsx:130` navigates straight to `/review`. The result summary with `Check my answers` described at `EXPERIENCE.md:30,156` does not exist.
- **Consequence:** in the walkthrough a seven-year-old would see three cards titled "Question 1/2/3", each ending in "Needs practice", with no way to tell which sentence each refers to. A per-question "Needs practice" also reads as a judgement on single items. Rendered evidence is in Behaviour Verification.
- **Disposition:** fix now (learner UX).

### Medium: player accessibility misses selected state, focus management and announcements

- **Source:**
  - `practice-player.tsx:139,145`: selection toggles only a CSS class, with no `aria-pressed` or radio semantics.
  - `practice-player.tsx:149`: changing question or opening the confirmation moves no focus and announces nothing. The walkthrough recorded focus remaining on `Next` and on `Submit practice`.
  - `practice-player.tsx:148`: every audio control is an unlabelled "Replay audio", including the first play.
  - `practice-player.tsx:146`: the note-taking hint is fixed text, not driven by the policy `inputKind`/`maxWords` (`EXPERIENCE.md:126` expects e.g. `Write one number`).
  - `practice-player.tsx:147`: word-bank `choice()` buttons have no React `key`; the walkthrough logged "Each child in a list should have a unique key prop".
- **Consequence:** WCAG 2.2 AA / NFR-2 risk. `DESIGN.md:125` and `EXPERIENCE.md:123-124` require selected and focus states that are programmatic and announced. Measured targets: True/False are 52px high, navigation 48px. They meet NFR-2's 48px minimum but not `DESIGN.md:78`'s 56px answer-option height.
- **Disposition:** fix now.

### Medium: learner-facing status copy is technical rather than child-friendly

- **Source:** `practice-player.tsx:138`, where the recovery messages include "Online. Your practice can save to the server." and "Recovery copy saved on this device.". The walkthrough showed this message in the most prominent block on every question, above the prompt.
- **Consequence:** it conflicts with the PRD guardrail of calm, concise, child-friendly language. The panel competes with the task itself, and "Saved." appears after every tap.
- **Disposition:** fix now, as a copy pass together with the accessibility work.

### Medium: learners cannot practise a set again, and Start again is missing

- **Source:**
  - `practice.ts:29` maps a set with a submitted attempt to the `Review` action only.
  - `learner-home.tsx:8` offers no other action.
  - No `Start again` exists, contrary to `EXPERIENCE.md:89`.
- **Consequence:** the PRD loop "learner practises again and progress is visible" cannot happen for any set already completed. The schema allows it (one *open* attempt per learner and set).
- **Disposition:** fix now, but needs the product decision recorded under Open Questions.

### Medium: retired and finalised attempts have broken entry points

- **Source:**
  - `repositories.ts:47`: learner home lists only `published` sets, so open or submitted attempts on a retired set lose their Resume/Review action.
  - `src/app/learner/practice/[setId]/attempt/[attemptId]/page.tsx:9` calls `notFound()` for `ATTEMPT_FINALISED`, so reloading after a lost submit response shows a 404 instead of the review.
  - Resume routes through preparation (`learner-home.tsx:8`), which rejects a retired snapshot.
- **Consequence:** grandfathered attempts (`EXPERIENCE.md:106`; SPEC:62) are reachable only by typed URL.
- **Disposition:** fix now.

### Medium: PWA namespace and offline media rely on fragile state

- **Source:**
  - `public/service-worker.js:3,28-29`: the active-account map lives only in worker memory and is set once by the player (`practice-player.tsx:52-53`). After the browser stops an idle worker, offline media requests return `Response.error()`.
  - `src/features/pwa/ui.tsx:12-20`: namespace purge runs only from the sign-out button (`identity/ui/sign-out-button.tsx:9`), not on session expiry, deactivation, or another learner signing in on the same device.
- **Consequence:** cached media can be unavailable during the long offline gaps Story 3.4 targets. The Story 3.2 criterion "account switch clears the prior account namespace" is met only for explicit sign-out.
- **Disposition:** fix now. Verified by reading only, not in a browser.

### Low: note-taking options reach the client

- **Source:** `repositories.ts:145,150` sends `options` for every engine. `src/features/content/domain/contracts.ts:42` requires at least one option for every engine, including `audio_note_taking`, which never displays them.
- **Consequence:** an author who places the answer in note-taking options leaks it in page data before submission (FR-8). This depends on content, and no validation prevents it.
- **Disposition:** fix now (cheap).

### Verification gap: no browser or database test of the learner flow beyond attempt start

- **Source:**
  - `tests/e2e/teacher-evidence.spec.ts:185-251` stops once the attempt page opens.
  - `tests/unit/practice-application.test.ts:111-116` checks idempotency against a mocked repository.
  - The service worker is checked by string matching (`tests/unit/pwa-cache-policy.test.ts:49-62`).
  - There are no component tests for the player, review or preparation UI.
- **Consequence:** answering, every engine's UI, offline recovery, the submit confirmation, review, cross-learner `ATTEMPT_SCOPE_MISMATCH`, stale revisions and finalised-write rejection through real routes are all unguarded. The blocking finding passed five story reviews for this reason.
- **Disposition:** fix now.
- **Prevention lesson:** a UI-bearing story is not done until one browser journey drives its new behaviour end to end. The same lesson was recorded for Epic 2's publication boundary and Epic 5's provisioning journey.

### Aggregate views

- **Architecture delta:** the epic kept the established feature layering (`application` → `infrastructure`, `ui` client components, API routes as thin adapters). No cycle or cross-feature infrastructure import was introduced. Learner-side labelling (`practice_attempt_evidence`) and teacher-side evidence (`submitted_evidence_facts`, Epic 4) are two independent projections of the same outcomes with different rules. That duplication is the structural cause of the recommendation divergence.
- **Size growth:** `practice-player.tsx` concentrates rendering, offline state machine, draft persistence, mutation queueing, playback and submission in one component. Its key logic sits on very long lines (`:138-151`). The interacting async paths (`save`, `request`, `submit`) are where the blocking and high findings live. Extracting a tested attempt-sync model is recommended alongside the fix.
- **Pattern divergence:** none material. Error codes, `PracticeResult` shapes and `no-store` responses follow the existing API conventions.
- **Spec reconciliation:**
  - **Fix:** result summary (`EXPERIENCE.md:30,156`), `Start again` (`:89`), review prompt reference (`:68`), recommendation explanation (`:51,61`), the PRD outcome-based evidence threshold.
  - **Accept as-is:** fixed 48px rather than 56px answer height. NFR-2's 48px is the normative minimum; `DESIGN.md` owns the 56px visual rule. Reconcile one way or the other in the accessibility action item rather than re-flagging.

### Checked and clean

- **No pre-submission answer leakage through the API.** The player selects no `answerPolicy` or `feedback` (`repositories.ts:145`), and `tests/integration/staff-publication-to-learner.test.ts` asserts the absence of answer fields.
- **Ownership.** Every attempt query is scoped by learner and set.
- **Database guards.** Migrations 0017-0020 block post-submission mutation and incomplete review snapshots. Start uses an advisory lock, `FOR UPDATE`, and a unique open-attempt index.
- **Service-worker cache scope.** No API, HTML, signed-token or review payloads are cached, and practice routes send `no-store`.
- **Media URL expiry.** The player's media is attempt-scoped, so the five-minute preparation token does not expire mid-attempt.
- **Draft identity.** Mismatched drafts are discarded, and stale revisions offer Reload latest / Leave.
- **Offline submit.** Blocked with honest copy and no queued request (also observed in the browser).
- **Number answers.** A typed digit string is converted before scoring (`repositories.ts:221`), so a typed `7` scores correctly.

## Action Items

All items are proposed remediation for the normal development loop. Items 3, 6 and 7 also carry a spec reconciliation or product decision, noted inline.

1. **Development:** make open-attempt answers server-authoritative before submission.
   - On reconnect and on draft hydration, mark locally newer answers as unsynced and resend them through the revision-aware save path.
   - Make `Submit practice` wait for every pending edit, including an unblurred note-taking field, and block submission while any answer is unsynced.
   - Count only server-confirmed answers in the confirmation.
   - Never skip a save silently while another is in flight.
   - Add a browser regression: answer offline → reconnect → submit → review shows the answer.
2. **Development:** replace the attempt-level learner evidence label with the PRD rule (per paper/part and language target, at least three assessable outcomes from the latest attempt of each set).
   - Exclude guidance IDs from practice areas.
   - Show a human-readable practice area (target label plus paper/part) instead of an ID.
   - Make recommended sets startable links.
   - Reuse or share the teacher evidence projection rather than maintaining a second rule.
3. **Development:** rebuild post-submission review as the experience contract describes.
   - Add a result summary with a `Check my answers` entry.
   - Show each item's prompt and media reference.
   - Use calm child-friendly outcome wording instead of raw outcome codes.
   - Remove the repeated set-level label from each question, or replace it with a per-target summary.
   - Add a "practice feedback, not an official result" statement.
   - Wording requires product review under the open `GATE-PUBLIC-WORDING` only if it becomes public-facing.
4. **Development:** fix player accessibility.
   - Selected state via `aria-pressed` or radio-group semantics.
   - Focus the question heading on navigation and the confirmation heading on open, and announce question changes.
   - Distinct `Play`/`Replay` labels per clip.
   - Policy-driven note-taking hint.
   - React keys for word-bank options.
   - Reconcile the 48px/56px answer-option height between NFR-2 and `DESIGN.md:78`.
5. **Development:** child-friendly copy pass for learner status, recovery, save, preparation and confirmation messages, keeping recovery honesty while moving technical detail out of the primary task area.
6. **Development** (needs the product decision under Open Questions): add `Practise again` for completed sets and `Start again` with confirmation for drafts (`EXPERIENCE.md:89`), preserving prior submitted attempts.
7. **Development:**
   - Keep Resume and Review available on learner home for retired sets that have the learner's open or submitted attempts.
   - Allow resuming a grandfathered open attempt without re-preparing a retired set.
   - Redirect a finalised attempt's player URL to its review instead of returning 404.
8. **Development:** harden PWA namespacing.
   - Persist or re-announce the active account so offline media survives a service-worker restart.
   - Purge the prior account namespace on session change, expiry and deactivation, not only on explicit sign-out.
9. **Development:** stop sending `options` for `audio_note_taking` items to the client, and reject note-taking options that contain an accepted answer during content validation.
10. **Development:** add learner-flow verification.
    - A browser journey per P0 engine: answer, change, save and leave, resume, offline, submit, review. Include audio with a test audio asset on the E2E media server.
    - Database-backed route tests for cross-learner scope mismatch, stale revision on save/playback/submit, same-key and different-key submission retry, and post-submission write rejection.
    - Process lesson: a UI-bearing story is done only when one browser journey drives its new behaviour.

## Acceptance Verdict

**Rejected.** Criteria are declared in `_bmad-output/planning-artifacts/epics.md:173-251`. All five stories are `done`, and the server-side guarantees (no pre-submission answers, ownership, immutability, idempotent deterministic scoring) hold. However:

- Story 3.4's recovery criterion is not met. Answers given offline or restored from a draft are silently recorded as unanswered, reproduced in the browser. This is a blocking pilot criterion ("answer-loss").
- Story 3.1's recommendation does not follow the PRD evidence rule and exposes internal IDs.
- Story 3.5's review omits the result summary and the question reference required by the experience contract.

A human decision may override this verdict.
